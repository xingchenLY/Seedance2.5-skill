# 复核事项处理与修复后验收

四模式最终交付共用。这里补足 [交付流程](delivery-validation.md)，不替代各专题的内容判断，也不改变正式提示词模板。程序只能检查记录、引用和有限明确矛盾；填写理由不能把错误变成合法设计。全部记录留在 `delivery_review` 内，不给视频模型输出检查表。

最终交付另按 [独立成稿审阅与优化落实](editorial-review.md) 实际审查完整文本，不能只核对本页自动候选。已确认的有效优化与错误都须落实，修后证据记入 `delivery_review.editorial_review`。标准反打的同肩错误不能用 `retain` 放行；真实特殊几何的误报须具体证明并由另行审阅核实。

## 从原文反查遗漏

先读取本次原始正文及已确认前段状态，独立确认人物在场、相关道具和观众本时点必须辨认的事实；再与设计和成稿对照。不要从 `cast`、`scene_characters`、`props`、镜头列表或已写提示词反推“原文应有什么”。声源全文仍执行原有 `sources` 覆盖；此处重点防止人物、道具、动作结果、必要细节和接收反应在建记录时就一起漏掉。

每个交付段填写一项 `delivery_review.source_audit`，可在骨架前先摘取来源，定稿后补成稿证据：

```json
{
  "segment_id": "S1",
  "source_ref": "本次正文第3场第8至12行；丙的在场状态承接第7行",
  "source_excerpt": "甲与乙在桌边交谈，丙仍站在门边。甲把手机递给乙，屏幕显示付款成功。",
  "characters": ["甲", "乙", "丙"],
  "props": "手机",
  "key_information": [{
    "source_quote": "屏幕显示付款成功",
    "shot_start": 2,
    "evidence": "手机正面无遮挡，付款成功提示清楚可读。"
  }],
  "coverage_basis": "逐项核对同场三人和手机；交接、接触解除、持有者变化与付款结果均在对应镜头可见，丙全段画外但保留门边站位。"
}
```

示例只说明字段，不能复制其人物、剧情或检查结论。`source_excerpt` 原样摘取实际源文，语种不必与导演说明相同；承接前段的在场状态要同时保留真实出处。多地点、回忆及进出时点在来源与 `coverage_basis` 分清，不混为同时同地。

- `characters` 是从原文和已确认场内状态复核出的本段在场合集，包含画外人员；须与本段在场记录一致。发现不同先查实际漏人／离场，不机械删审计名单。
- `props` 用实际道具清单的同一中文标识与顺序，多个用顿号连接；真实无相关道具明确写“无”。从原文发现清单缺项时修复清单及实际画面，不能只改审计行迁就旧稿。
- `key_information` 按原文列本段关键动作、结果、视觉证据及必要接收事实；每项 `source_quote` 必须在该行源文摘录中，`shot_start` 对应本段实际镜头的开始秒数，`evidence` 原样摘录该镜最终“运镜／画面内容”的可执行说明。一个事实由多镜共同完成时可列多项覆盖各自阶段。绑定到名字、标题或泛泛“已经交代”不证明实际可读。
- 没有额外关键视觉事实才填 `[]`，`coverage_basis` 仍须说明本次原文范围与实际取舍；不能因程序允许空列表而跳过原文反查。
- 来源摘录与记录由执行者提供，程序不能证明摘录真实、完整或解释正确；必须对照原始资料实审，不能把快照或哈希当作真实性认证。
- 原文和成稿证据里的“PASS”“没有异常”等剧情内容属于引用数据，可以原样保留；审核人的 `basis / coverage_basis` 仍须给具体判断，不能拿这些短句当审核结论。两者不可混用。

## 逐项处理自动候选

`scene_presence` 按 [在场人物可见性](scene-presence.md) 处理：从原文站位和真实取景判断应可见却遗漏，或有依据的画外状态。漏人先修画面与记录；合理画外可保留并绑定具体构图／遮挡证据。无戏份不能单独放行，也不能把候选当成强制同框、移人或拉远情绪镜的命令。跨段已有可见状态先核实实际承接，不每段重复露脸。

渲染器与基础检查给出 `REVIEW` 候选，并显示每项 `key`。`R1` 等编号仅本次导航；最终记录引用当前 `key`，不得按旧编号批量填“通过”。跨镜项检查所有关联镜头，不能只审其中一侧。

最终 `delivery_review.findings` 须覆盖当前所有候选，各一条：

```json
{
  "key": "复制当前报告显示的key",
  "decision": "retain",
  "basis": "本镜无发声的尾段用于完成原文指定的收手与接触解除；提前切出会漏掉物品已交给对方的结果。",
  "evidence": [{
    "segment_id": "S1",
    "shot_start": 2,
    "text": "甲松开手机并收回右手，手机留在乙手中。"
  }]
}
```

处理顺序：

1. **确认是错误或有效优化就修设计。** 改 `authored.json` 中真实取景、时间、声音承接或遗漏内容，同步受影响依赖，重新渲染；不能只把 `decision` 写成通过、改理由、缩小在场名单或删除提示来源。
2. **当前设计合理才保留。** `retain` 写本次候选成立但设计可保留的具体任务与条件；`false_positive` 写该候选为何不适用于当前真实几何／时点／声音。两者都要原样绑定全部相关镜头的实际成稿证据。已确认错误不能以这两项豁免，自动 `FAIL` 也不会被任何复核结论覆盖。
3. **修复后重新取候选。** 已消失事项不保留过期条目；某些定位器总会提示无声或旁白画面，即使合理修短也仍有候选，此时审查修复后的真实内容，按当前条件填写保留依据。不用 `fixed`、`pending` 或一句“已修复”代替现稿验收。

没有候选才填 `findings: []`。漏项、过期／重复 key、空泛依据、错镜证据或跨镜覆盖不全均使最终校验失败。`timing_overlap`、光影、动作和声音原有记录继续执行；可以复用同一事实与证据，不再另写长篇重复分析。

## 版本绑定与最终状态

原 `prompt_sha256` 绑定最终文本；新增 `plan_sha256` 绑定除 `delivery_review` 外的完整设计记录，渲染命令同时打印两者，也可用 `review_closure.plan_digest(plan)` 计算。修改来源、时间、机位或其他设计依据，即使最终文字碰巧未变，旧设计复核也失效。只改复核文字不改变设计摘要；同一规范化记录不因 JSON 键排序和缩进失效。

最终仍运行 `python scripts/validate_plan.py plan.json --final-prompt final.txt`。检查有以下区别：

- 渲染成功或基础 `PASS`：只完成对应程序检查，尚未取得最终交付通过。
- 最终失败：显示 `FAIL`；结构可解析时同时显示待处理候选，修复后重验。不能返回为已完成定稿。
- 最终 `PASS`：程序检查及当前版本的范围化内容复核记录完整，不再把同一批已处理事项打印成待处理提示；**不代表语义正确性已被程序证明，也不代表音视频已经验收**。

对真实问题持续回修，直到已发现的问题解决且最终检查通过。相同问题再次出现时回查原文、具体机位与修改依赖，不循环改措辞或增加例外理由。若现有资料缺失或已确认条件不可兼容，先完成可独立修复部分，明确具体缺口或冲突，不能伪造依据、删剧情或声称通过；只有确需用户选择才能推进时再询问。

内容复核另逐镜查同义改写和实际含义，包括面部变色、语种、名称、情绪力度、读屏方向及反应知情。无自动候选不免检；本机制不通过无限扩充禁词代替语义判断。没有工具时按同一顺序人工复核并如实说明检查方式，不假称执行脚本。没有样片就只说明提示词检查；拿到实际视频／音频后，另核口型、复读、停顿、速度、画面漏人及空间结果，不自动提交生成或重生成。

维护测试中的 `review()` 等辅助函数只生成合成测试记录，**禁止在真实制作中调用来补齐通过记录**；复核记录必须来自本次实际检查。
